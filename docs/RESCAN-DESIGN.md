# Проект: пересканирование библиотеки без рестарта (#39)

Статус: этапы 1–3 реализованы 2026-10-06; этапы 4–5 отложены. Решения по разделу «Вопросы» (2026-10-06): периодическое сканирование по умолчанию выключено; сохранённый индекс пока не нужен; публикация пустого тома отменяется; дата добавления — время первого обнаружения пути в текущем процессе (при старте — mtime, до появления индекса).

## Сейчас

- `cmd/coach/main.go` сканирует `-media-dir` до запуска HTTP: последовательно, FFprobe до 15 с на файл, до 10 минут на всё; при ошибке сервер не стартует.
- Каталог (`media.Catalog`) живёт в памяти и передаётся в `server.New`. Обработчики читают поле `s.media` 41 раз в 6 файлах (`catalog.go`, `dto.go`, `home.go`, `images.go`, `playback.go`, `series.go`), иногда несколько раз за запрос.
- `Catalog` держит открытый `os.Root` каталога медиа; поток и обложки открываются через него.
- ID элемента — хеш абсолютного пути библиотеки и относительного пути файла, ID сериала и сезона — хеш пути папки. Повторное сканирование тех же путей даёт те же ID; состояние пользователя (`state.json`) хранится по ID и не зависит от каталога.
- `DateCreated` равен mtime файла.

## Требования (из #39)

1. Добавленные, изменённые и удалённые файлы видны без рестарта, без дублей.
2. ID неизменных элементов сохраняются; один битый файл не прерывает обход.
3. Каталог переживает принудительную остановку.
4. Сканирование во время воспроизведения — отдельно, #30.

## Предлагаемое решение

### 1. Снимок каталога вместо поля

`Server` хранит `atomic.Pointer[media.Catalog]`. Каждая функция берёт один снимок (`catalog := s.catalog()`) и использует только его, поэтому цикл не индексирует подменённый срез. Реализовано по функциям, а не по запросу: запрос, совпавший с публикацией, может взять в разных функциях два соседних снимка и временно показать неточные счётчики; ошибок это не даёт. Каталоги неизменяемы после публикации.

`os.Root` открывается один раз при старте и разделяется всеми снимками: путь библиотеки не меняется, поэтому корень не нужно закрывать при замене снимка, а уже открытые потоки не зависят от того, какой снимок их открыл.

Это механическая замена 41 обращения; поведение не меняется. Отдельный этап с прежними тестами.

### 2. Инкрементальное сканирование

`media.Rescan(ctx, previous)` обходит каталог так же, как сейчас, но для файла с тем же относительным путём, размером и mtime берёт результат FFprobe из предыдущего снимка, а не вызывает FFprobe. Новые и изменённые файлы пробуются; отсутствующие выпадают. ID считаются как сейчас, поэтому неизменные элементы сохраняют ID, а дублей нет по построению: ключ — путь.

Битые файлы, как и сейчас, пропускаются со счётчиком. Ошибки обхода (нечитаемый корень или подкаталог, превышение лимитов, таймаут) отменяют публикацию: остаётся прежний снимок, в журнал пишется причина.

### 3. Когда сканировать

- При старте: если есть сохранённый индекс (п. 4) — сервер стартует сразу с ним, а сканирование идёт в фоне; без индекса — как сейчас, до запуска HTTP.
- Периодически: флаг `-rescan-interval` (например, `30m`; `0` — выключено).
- Вручную: `SIGHUP` процессу. HTTP-маршрут не предлагается: Emby Web 4.10.0.40 не вызывает `Library/Refresh` (#34), сканирование библиотеки там — на страницах администратора (#33), а у Coach один пользователь без этих прав.
- Одновременно идёт не больше одного сканирования; запрос на сканирование во время текущего откладывается до его конца.

Отслеживание событий файловой системы (inotify/kqueue) не предлагается в первой версии: на сетевых томах NAS (SMB/NFS) оно ненадёжно и требует зависимости.

### 4. Сохранённый индекс

После каждой успешной публикации каталог записывается в `<data>/catalog.json` атомарно (временный файл, fsync, rename — как `state.json`). Формат версионируется; несовместимая или повреждённая версия игнорируется и приводит к полному сканированию, не к отказу старта. Индекс хранит результаты FFprobe и время первого обнаружения каждого пути.

Это закрывает требование 3, ускоряет старт и даёт настоящую дату добавления: `DateCreated` = время первого обнаружения пути, а не mtime (Latest сортируется по добавлению, как в Emby). Для уже существующих файлов при первом запуске с индексом берётся mtime, чтобы порядок не перевернулся.

### 5. Защита от исчезнувшего тома

Если корень `-media-dir` читается, но новый обход не находит ни одного видео, а прежний снимок был непустым, публикация отменяется с предупреждением: так выглядит отмонтированный том NAS, и удаление всей библиотеки было бы ошибкой. Состояние пользователя при этом не трогается в любом случае.

### 6. Уведомление клиентов

После публикации Emby отправляет по WebSocket `LibraryChanged` (добавленные, изменённые, удалённые ID). Emby Web по нему обновляет открытые экраны. Предлагается последним этапом вместе с #25; без него изменения видны после перехода по экранам или перезагрузки.

## Этапы

| # | Этап | Проверка |
|---|---|---|
| 1 | Снимок каталога через `atomic.Pointer`, общий `os.Root` | прежние тесты, `-race` |
| 2 | `Rescan` с повторным использованием FFprobe | модульные тесты с подменным probe: добавление, изменение, удаление, сохранение ID, отказ при ошибке обхода |
| 3 | Фоновое сканирование: интервал, `SIGHUP`, одно одновременно, защита от пустого тома | тесты; браузер: добавленный файл появляется без рестарта |
| 4 | `catalog.json`: запись, загрузка при старте, дата первого обнаружения | тесты на повреждённый и устаревший индекс; рестарт стартует без ожидания FFprobe |
| 5 | `LibraryChanged` по WebSocket | браузер: открытая библиотека обновляется (#25) |

Каждый этап — отдельный коммит, работоспособный сам по себе.

## Вопросы

1. Интервал по умолчанию: выключено (только `SIGHUP` и старт) или, например, 30 минут?
2. Нужен ли сохранённый индекс сейчас (этап 4) или достаточно этапов 1–3?
3. Защита от пустого тома (п. 5): отменять публикацию, как предложено, или публиковать пустой каталог?
4. Дата добавления: переходить на время первого обнаружения (п. 4) или оставить mtime?
