# Coach

Go-backend для совместимости с Emby Web: локальная учётная запись, сессии, настройки, фильмы и базовая иерархия сериалов, прямая HTTP-выдача видео и сохранение позиции. Медиатека доступна только для чтения.

Эталон — Emby Web **4.10.0.40**. Проверены оригинальные API-модули и браузерный сценарий «поиск → карточка → play → seek → stop → рестарт → resume»; границы проверки описаны в [VALIDATION.md](docs/VALIDATION.md). Это прототип, не замена рабочего Emby. Снижение расхода ресурсов относительно Emby ещё не измерено.

## Запуск

Нужны Go 1.25+ и Linux/macOS.

```sh
go build -o bin/coach ./cmd/coach
```

Создать локального пользователя. Пароль передаётся через stdin, минимум 12 байт. Пример для текущей оболочки zsh; ввод скрыт и не попадает в историю команд:

```zsh
read -rs 'coach_password?Пароль нового пользователя Coach: '
printf '\n'
printf '%s\n' "$coach_password" | ./bin/coach -init -username viewer
unset coach_password
```

Запустить сервер с полной локальной копией Emby Web:

```sh
./bin/coach -web-dir ../emby-webui
```

Адрес: <http://127.0.0.1:8097/>. Пользователь `viewer` и пароль, заданный выше, принадлежат Coach; учётные записи Emby не импортируются.

`-web-dir` указывает папку с `index.html`, а не её родителя. Coach читает UI без изменений; в выдаваемый исходный `<html>` добавляет `data-appversion="4.10.0.40"`. Это настройка загрузчика, не автоматическое определение версии произвольного UI. Предоставленные API-модули совпадают с эталоном 4.10.0.40. В предоставленной копии не хватало четырёх файлов, которые клиент загружает при старте: `modules/apphost.js`, `modules/input/keyboard.js`, `modules/virtual-scroller/virtual-scroller.js` и `.css`; 2026-10-06 они скопированы с эталонного Emby 4.10.0.40, и Emby Web с `-web-dir` запускается (#19). Из остальных 307 файлов, которые клиент загружает на главной, в библиотеках, поиске, на страницах сериала и фильма, во всех пользовательских настройках и в экране воспроизведения, 306 побайтно совпадают с эталоном; `settings/appgeneral.html` отличается только кодировкой подписи «Norwegian Bokmål» (сверка 2026-10-04). Раздаются только статические файлы внутри выбранного каталога, без листинга, скрытых файлов и выхода через symlink. Не указывайте папку с приватными данными: разрешённые HTML/JS/JSON и другие ресурсы доступны без входа. Файлы UI не включаются в бинарник или репозиторий Coach.

Альтернатива — `-web-upstream http://192.168.1.11:8096`: `/web/*` получает статические файлы исходного Emby по GET/HEAD. Токены, cookies, тело запроса и произвольные query-параметры upstream не передаются; перенаправления не выполняются. Одновременно к Emby идут не больше 16 запросов, остальные ждут свободного места до 10 секунд и затем получают 503 с `Retry-After`; файл больше 32 МиБ не отдаётся. Кеша нет. Этот режим требует доступного Emby. `-web-dir` не обращается к нему за ресурсами; внешние обращения самого клиента отдельно не блокируются.

Параметры `-web-dir` и `-web-upstream` взаимоисключающие. Без обоих доступны только API и информация на `/`. Авторизацию, каталог и видео во всех режимах обслуживает Coach.

Другие параметры: `-listen` (по умолчанию `127.0.0.1:8097`), `-data` (`./data`), `-name` (`Coach`). Слушатель по умолчанию локальный; TLS и работа за reverse proxy ещё не настроены.

### Контейнер

[Dockerfile](Dockerfile) собирает образ: статический `coach` на Alpine 3.24 с FFmpeg/FFprobe 8.1 (протокол `fd`, `libx264`, `aac`). Процесс работает от пользователя `coach` (UID 10001), состояние хранится в томе `/data`, внутри контейнера слушается `:8097`. Пример для Podman; Docker принимает те же команды:

```sh
podman build -t coach .
read -rs 'coach_password?Пароль нового пользователя Coach: '
printf '\n'
printf '%s\n' "$coach_password" | podman run --rm -i -v coach-data:/data coach -init -username viewer
unset coach_password
podman run -d --name coach -p 127.0.0.1:8097:8097 -v coach-data:/data -v /absolute/path/to/media:/media:ro coach -listen :8097 -media-dir /media -web-upstream http://192.168.1.11:8096
```

Аргументы после имени образа заменяют `-listen :8097`, поэтому `-listen` указывается явно; `-data /data` задан в образе. Для `-web-dir` каталог Emby Web монтируется отдельно (например, `-v /absolute/path/to/emby-webui:/web:ro` и `-web-dir /web`). Пересканирование: `podman kill -s HUP coach`. Ограничение частоты входа считает адрес клиента так, как его видит контейнер; при пробросе порта это может быть общий адрес шлюза.

`scripts/check-container.sh IMAGE` проверяет образ: `-init`, сканирование MKV H.264 + AC3 и remux в HLS (FFprobe читает `h264` + `aac`), остановку с кодом 0. По умолчанию используется Docker, Podman — через `CONTAINER=podman`. Нужны `curl` и `jq`.

## Каталог фильмов и сериалов

Для сканирования указать одну тестовую папку и установить FFprobe с поддержкой протокола `fd`:

```sh
./bin/coach -media-dir /absolute/path/to/test-movies -web-dir ../emby-webui
```

Сканирование выполняется перед запуском HTTP-сервера. Повторное сканирование без рестарта запускается сигналом `SIGHUP` (`kill -HUP <pid>`) и, если задан `-rescan-interval` (например, `30m`, не меньше `1m`), периодически; по умолчанию периодического сканирования нет. При повторном сканировании файлы с тем же путём, размером и mtime не проходят FFprobe заново; добавленные, изменённые и удалённые файлы видны после публикации нового каталога, ID неизменных путей сохраняются. Одновременно идёт одно сканирование: `SIGHUP` во время сканирования запускает ещё одно после него. Ошибка обхода, превышение лимитов или каталог, в котором вдруг не осталось ни одного видео (так выглядит отмонтированный том NAS), не публикуются: остаётся прежний каталог, в журнал пишется `Media rescan failed; keeping the previous catalog`. Открытые экраны Emby Web не обновляются сами: изменения видны после перехода по экранам или перезагрузки (`LibraryChanged` по WebSocket не отправляется). Без `-media-dir` библиотека остаётся пустой; FFprobe не требуется. Исходные файлы не изменяются. Файлы объединяются в `Movies`, кроме явно распознанных эпизодов.

Структура `Show/Season 01/Show.S01E02.mp4` внутри `-media-dir` создаёт библиотеку `TV Shows`, сериал, сезон и эпизод. Номер сезона в папке и имени должен совпадать; `Season 00` поддерживается. Остальные имена остаются фильмами. ID фильмов не меняются; ID сериалов/сезонов стабильны при неизменном пути. Поддержаны карточки, поиск, Seasons/Episodes, прямая выдача эпизодов; «Воспроизвести» на сериале проигрывает эпизоды по порядку в очереди клиента. `Shows/NextUp` для каждого начатого сериала возвращает эпизод после самого дальнего просмотренного; сериалы упорядочены по последнему просмотру, спецвыпуски `Season 00` не учитываются. Строка Continue Watching на главной (`Sections/resume/Items`, раздел объявляет `IncludeNextUpInResume`) и `Items/Resume` добавляют эти эпизоды к начатым элементам (как у эталонного Emby, `Items/Resume` добавляет их и без `IncludeNextUp`; исключает только `IncludeNextUp=false` — это допущение, не снято); при сортировке по дате просмотра эпизод получает дату последнего просмотра своего сериала. Этот порядок — допущение: ответ Emby не снят. Альтернативные схемы имён и онлайн-метаданные не реализованы. Заголовки строк главного экрана следуют `X-Emby-Language` для русского, немецкого, французского, испанского и итальянского (формулировки клиента Emby Web), для остальных языков — английские. Переводы лежат в `internal/server/locales/<язык>.yaml` (ключ: текст, ключи — строки Emby Web) и встраиваются в бинарник; `en.yaml` содержит все ключи и служит запасным языком. Новый язык — новый файл; тест проверяет, что в нём нет ключей, которых нет в `en.yaml`, и пустых значений. Названия элементов не переводятся: источника локализованных названий нет, показывается исходное название.

- Расширения: mp4, m4v, mkv, webm, avi, mov, mpg, mpeg, ts, m2ts, wmv, ogv. Нужна обнаруженная видеодорожка; битые файлы пропускаются и учитываются в журнале счётчиком без путей.
- Название берётся из имени файла; FFprobe даёт длительность, кодеки, размеры кадра, аудио- и субтитровые дорожки. NFO и внешние провайдеры пока отсутствуют.
- ID зависит от абсолютного пути библиотеки и относительного пути файла: сохраняется при рестарте, меняется при переносе/переименовании. `DateCreated` — время, когда Coach впервые увидел путь: для файлов, найденных при старте, — время изменения файла, для найденных повторным сканированием — время этого сканирования. Latest и сортировка по DateCreated используют его. Дата не сохраняется на диск: после рестарта она снова равна времени изменения файла.
- Каталог хранится в памяти, отдельно от `state.json`. Постоянного индекса нет: каждый старт сканирует всю библиотеку с FFprobe. Изменение файла с сохранением размера и mtime повторным сканированием не обнаруживается.
- Лимиты: 10 000 видеофайлов, 100 000 записей обхода, глубина 64, сканирование до 10 минут; один FFprobe одновременно, до 15 секунд и 1 MiB JSON на файл. Превышение общего лимита останавливает запуск (при повторном сканировании — оставляет прежний каталог), а не публикует неполный каталог. Таймаут не гарантирует прерывания зависшего файлового I/O ОС.
- Символические ссылки и специальные файлы не обходятся. Файлы открываются внутри `os.Root`; FFprobe получает дескриптор, а не путь. Разрешён только протокол `fd`, без сетевых запросов и открытия соседних файлов. Это ограничение доступа, не полная песочница для FFprobe.

Поддержаны поиск по имени, ParentId, Recursive, IDs/исключения, типы медиа и базовые фильтры. Сортировка — список полей через запятую из Name/SortName, DateCreated, DatePlayed, DateLastSearched, Runtime, ParentIndexNumber, IndexNumber, SeriesSortName, IsFolder (папки первыми) и Filename; поля сравниваются по порядку, `SortOrder` общий. `IsSpecialEpisode` отбирает эпизоды `Season 00`. `LiveTv/Programs` и `Movies/Recommendations` всегда пусты: Live TV и рекомендаций нет. Страница по умолчанию содержит до 100 элементов, Latest — 20; `Limit` от 0 до 1000. Неизвестные фильтры/сортировки возвращают 400. Позиция, число запусков, отметки «просмотрено» и «избранное» сохраняются в состоянии пользователя. Отметка «просмотрено» на сериале или сезоне ставится и снимается у всех его эпизодов; сериал и сезон считаются просмотренными, когда просмотрены все эпизоды, и сообщают `UnplayedItemCount`. «Убрать из продолжения просмотра» (`HideFromResume`) обнуляет сохранённую позицию и помечает элемент скрытым, чтобы он не возвращался как следующий эпизод; пометка снимается при следующем воспроизведении или `Hide=false`, позиция не восстанавливается. Строка главной отдаёт не более 1000 элементов: больший `Limit` (меню карточки запрашивает 5000) сокращается, а не отклоняется.

## Обложки

Primary-обложки читаются из локальных `.jpg`, `.jpeg`, `.png` (расширения в нижнем регистре). Для видео порядок поиска: `<имя без расширения>-poster`, `<имя без расширения>`, затем `poster` и `folder` в той же папке. Для сериалов/сезонов — `poster` и `folder` в их папке.

Лимиты: файл до 8 MiB, заголовок до 1 MiB, сторона до 16 384 пикселей, площадь до 32 млн пикселей. Доступ ограничен корнем медиатеки; пиксели не декодируются сервером. Отдаётся оригинал без resize, quality-преобразований, overlays и backdrop.

Emby Web получает подписанный ImageTag и передаёт его в `tag` без API-токена. Ссылка разрешает только конкретную ревизию обложки и действует до logout/истечения сессии; штатный рестарт её сохраняет. Не публикуйте такие ссылки: это ограниченные ключи доступа. Обычный API-токен также принимается. Авторизация проверяется до ответа 304; кеш приватный, с обязательной перепроверкой. Ревизия и слабый ETag зависят от пути, размера и mtime, не от содержимого: замена с сохранением размера/mtime не обнаруживается.

Смена пароля: `POST /Users/{id}/Password` с `CurrentPw` и `NewPw` (12–1024 байт) проверяет текущий пароль с тем же ограничением частоты, что и вход; текущая сессия остаётся, остальные отзываются. Emby Web 4.10 для серверов от 4.8.0.38 скрывает поле текущего пароля и отправляет его пустым. По решению #46 Coach по-прежнему требует текущий пароль: пустой отклоняется с 400, неверный — с 401 (текстовое сообщение); форма профиля показывает общую ошибку клиента «Недопустимое имя пользователя или пароль», сессия сохраняется.

Аватар пользователя загружается и удаляется на странице профиля Emby Web. Принимаются JPEG и PNG с теми же лимитами, что у обложек; файл хранится как загружен, в каталоге `-data` рядом с `state.json` (`user-image-<ревизия>`). Ревизия — хеш содержимого. `PrimaryImageTag` подписан так же, как ImageTag обложки, и не подходит для изображений элементов.

## Воспроизведение

Coach отдаёт исходный файл через Direct Stream: поддержаны GET/HEAD, Range, 206/416 и Resume. Если клиент не принимает файл как есть, но его HLS-профиль (`TranscodingProfiles`: `Protocol=hls`, `Container=ts`) принимает видеокодек, Coach делает remux в HLS: видео копируется без перекодирования, аудио копируется, если профиль принимает его кодек, иначе кодируется в AAC (каналы — до `MaxAudioChannels`, без него стерео). PlaybackInfo отдаёт `TranscodingUrl` (`/videos/{id}/master.m3u8?...`, токен в ссылке, как у потока), `TranscodingSubProtocol=hls`, `TranscodingContainer=ts`. Плейлист `main.m3u8` — VOD на весь фильм, сегменты MPEG-TS режутся по ключевым кадрам исходника, не короче 6 секунд; для этого FFprobe при первом запросе читает весь файл (список кешируется в памяти до 64 файлов; PlaybackInfo запускает чтение заранее). Перемотка за пределы готового перезапускает FFmpeg с нужного сегмента, отметки времени совпадают с непрерывным проходом. Ограничения: две сессии remux одновременно (третья получает `RateLimitExceeded`, запрос HLS — 503), сегменты лежат в `<data>/transcode` (очищается при старте и остановке), сессия хранит до 2 ГиБ; FFmpeg приостанавливается (SIGSTOP), уйдя на 10 сегментов вперёд, и продолжает, когда клиент догоняет; старые сегменты удаляются. Сессия завершается по `Sessions/Playing/Stopped`, `Videos/ActiveEncodings/Delete` (`POST`, или `DELETE Videos/ActiveEncodings`; без `PlaySessionId` — все сессии вызывающего), logout или через минуту без запросов. Без FFmpeg в PATH remux выключен. Перекодирование видео (несовместимый кодек, превышение битрейта, HEVC 10-bit для браузера) не реализовано (#22): тогда ответ — `NoCompatibleStream`. Совместимость по-прежнему зависит от контейнера, кодеков и клиента. Превью при перемотке не создаются: `ThumbnailSet` возвращает пустой набор. Команда «Скачать» (`Items/{id}/Download`) отдаёт исходный файл вложением; имя файла — название элемента с исходным расширением.

PlaybackInfo читает параметры из query и JSON, включая JSON с `text/plain`. Учитывает `EnableDirectStream`, лимиты битрейта/каналов, источник и аудиодорожку (не первую дорожку Emby Web в Chromium принимает только через remux в HLS: его профиль ставит условие `IsSecondaryAudio`); отклоняет конфликтующие значения, чужой UserId и неверные индексы. `StartTimeTicks` проверяется, но файл не обрезается: при прямой выдаче перемотку делает клиент через Range.

Профиль проверяется по DirectPlayProfiles, ContainerProfiles и CodecProfiles/ApplyConditions. Поддержаны сравнения Equals/NotEquals/EqualsAny/LessThanEqual/GreaterThanEqual и основные параметры видео/аудио: разрешение, уровень/профиль/тег кодека, битрейт, частота кадров, каналы и sample rate. Недостающие обязательные метаданные не считаются совместимыми; необязательные условия без метаданных пропускаются. По умолчанию условие обязательное. Отсутствующий DeviceProfile сохраняет режим discovery, явно пустой не разрешает воспроизведение.

При несовместимости ответ содержит `ErrorCode=NoCompatibleStream` без URL потока. Внешние субтитры рядом с видео (`Movie.srt`, `Movie.ru.srt`, `Movie.en.forced.srt`, `Movie.ru.sdh.srt`; также `.vtt`) добавляются при сканировании как дорожки после встроенных: язык — первая метка из 2–3 латинских букв, `forced`, `sdh`/`hi`/`cc` и `default` задают флаги; регистр букв в имени не важен; если имя подходит к двум видео, файл получает видео с более длинным именем, а видео с одинаковым именем (`Movie.mp4` и `Movie.mkv`) получают его оба. SRT с концами строк CR, CRLF или LF поддерживаются. PlaybackInfo отдаёт их с `DeliveryMethod=External` и ссылкой на WebVTT (`/Videos/{id}/{source}/Subtitles/{index}/Stream.vtt`, токен в ссылке, как у потока); SRT преобразуется в WebVTT на лету. Поддерживается только UTF-8 (с BOM или без): файл в другой кодировке (например, Windows-1251) не отдаётся, в журнал пишется `Subtitle unavailable`. До 32 файлов на видео, до 10 МиБ на файл. Встроенные текстовые субтитры (SubRip, mov_text, WebVTT, ASS/SSA) отдаются по той же ссылке: при запросе FFmpeg извлекает дорожку в WebVTT через канал, без временных файлов. Одновременно идут не больше двух извлечений, остальные ждут свободного места, пока клиент не отменит запрос; задание ограничено 2 минутами и 10 МиБ вывода и завершается при обрыве соединения; сбой FFmpeg даёт 404 и предупреждение `Subtitle unavailable`. Без FFmpeg в PATH и для графических субтитров (PGS, DVD, DVB) выбранная дорожка пропускается: видео идёт прямым потоком без субтитров (`DefaultSubtitleStreamIndex=-1`), в журнал пишется `Subtitle not deliverable, playing without it`; прожиг в видео не реализован. Извлечённые субтитры не кешируются: файл читается целиком при каждом запуске с ними. Если клиент не выбрал дорожку сам, Coach выбирает её по режиму субтитров пользователя (описания режимов взяты из Emby Web): «По умолчанию» — дорожки с флагом forced или default (forced первыми), «Умный» — дорожка предпочитаемого языка, если язык аудио другой, «Только форсированные», «Слабослышащие» — дорожки предпочитаемого языка, SDH первыми, «Всегда» — дорожки предпочитаемого языка, «Без субтитров». Языки сравниваются по списку `Localization/Cultures` (`ru` = `rus`), порядок предпочтений учитывается; выбираются только дорожки, которые Coach может отдать. Правила по описаниям, а не по снятым ответам эталона. Выбор аудио отражается в DefaultAudioStreamIndex, но файл не меняется: клиент должен уметь выбрать дорожку нативно. HDR, rotation и весь набор ограничений Emby ещё не покрыты.

Таймаут записи 30 секунд обновляется на каждом блоке: он ограничивает зависшую запись, а не длительность всей передачи. Файл не загружается целиком в память. Валидаторы кеша берутся из текущего размера/mtime; ETag слабый, не хеш содержимого, поэтому `If-Range` с ETag приводит к полной выдаче. Не изменяйте файл во время просмотра; метаданные каталога обновляются при рестарте или повторном сканировании.

При остановке на ≥90 % видео помечается просмотренным, позиция сбрасывается. Отсутствующий PositionTicks сохраняет позицию; отрицательный отклоняется. Для отчётов с PlaySessionId сохраняются последние 64 начала просмотра на клиентскую сессию: повтор start не увеличивает счётчик; progress/stop принимаются только для последнего незавершённого просмотра. Внутри него отчёты применяются по порядку получения, включая seek назад. Без PlaySessionId сохраняется прежняя семантика порядка получения, без дедупликации. Окно переживает рестарт; повтор старта, уже вытесненного из окна, считается новым. Отброшенный отчёт всё равно получает 204, но в журнал пишется предупреждение `Playback report ignored` с типом события, причиной и ID элемента; stop без позиции отмечается сообщением `Playback stopped without a position`. Графические субтитры и полная медиасовместимость ещё не реализованы.

## Реализованный контракт

API принимает маршруты без префикса и с `/emby/`, без учёта регистра. Значения query-параметров сохраняются без изменения.

| Область | Маршруты |
|---|---|
| Подключение | `GET /System/Info/Public`, `GET /Users/Public`, branding, ping |
| Вход | `POST /Users/AuthenticateByName`: JSON или form-urlencoded |
| Сессия | `GET /System/Info`, `GET /Users/{id}`, `GET /Users/Me`, `GET /Sessions`, `POST /Sessions/Logout` |
| Возможности клиента | `POST /Sessions/Capabilities/Full` |
| Настройки | `GET/POST /usersettings/{id}`, `POST /usersettings/{id}/Partial`, пользовательская Configuration |
| Каталог | Views, Items, ItemTypes для поиска, Items/{id}, Latest, root, Shows/{id}/Seasons и Episodes, Shows/NextUp; фильтры по сохранённым Played/Favorite; история поиска (`POST /Users/{id}/SearchedItems`, `POST /Users/{id}/RecentlySearched/Delete`, `WasSearched`, `SortBy=DateLastSearched`); пагинация Resume |
| Обложки | GET/HEAD Items/{id}/Images/Primary[/0], подписанные ImageTags или API-токен |
| Главный экран | HomeSections, Sections/{id}/Items, Resume |
| Настройки пользователя | `GET /Localization/Cultures` — список языков эталонного Emby 4.10.0.40 (196 записей, снят только для чтения 2026-10-04) для выбора языка субтитров и аудио |
| Воспроизведение | PlaybackInfo, Videos/{id}/stream.*, Videos/{id}/master.m3u8 и main.m3u8, Videos/ActiveEncodings, Sessions/Playing, /Progress, /Stopped |
| Состояние просмотра | POST/DELETE PlayedItems и FavoriteItems |
| WebSocket | `/embywebsocket`: вход по токену, KeepAlive, ping/pong, UserDataChanged |
| Пока пустые результаты | Upcoming, Missing (пропущенных эпизодов Coach не знает: нет онлайн-метаданных), Live TV recordings; Items с `MinPremiereDate` или `IsUnaired=true` (дат премьер нет) |

Поддерживаются токены в заголовках, query `X-Emby-Token`/`api_key`, а также `Authorization: Emby …` и `MediaBrowser …`. Конфликтующие токены отклоняются. JSON, отправляемый клиентом как `text/plain` с `reqformat=json`, поддержан. Неизвестные маршруты возвращают 404. Ошибки, как у эталонного Emby, возвращаются как `text/plain` с понятным сообщением, которое Emby Web показывает в диалоге.

Поле API `Version=4.10.0.40` выбирает соответствующую ветку протокола клиента. Версия Coach — `0.1.0`, видна в `/healthz`, `X-Coach-Version` и авторизованном `/System/Info`. Совпадение номера протокола не означает полную совместимость с Emby.

## OpenAPI-контракт

[api/openapi.yaml](api/openapi.yaml) — контракт Coach. Он один раз получен из OpenAPI-документа, который публикует сам Emby Server 4.10.0.40 (`GET /emby/openapi.json`; версия и SHA-256 исходника записаны в `info.x-coach-derived-from`), и дальше ведётся вручную. Это производная работа от спецификации Emby. В контракте все 526 операций Emby и Coach-only `GET /healthz`.

Отличия от исходника:

- оставлен только JSON, варианты `application/xml` удалены;
- адрес эталонного сервера удалён из `servers`;
- поправки, подтверждённые фикстурами, клиентом или приёмкой, помечены `x-coach-source`. Сейчас это публичные операции до входа (Emby помечает их защищёнными) и JSON-тело `POST /UserSettings/{id}/Partial`.

В схемах Emby нет `required`, поэтому проверяются только типы и enum, но не наличие полей. Каждый успех без тела документирован как `200`. Таблица выше описывает фактически реализованное; что ещё не реализовано, видно по списку ожидаемых падений e2e.

## Хранение и ограничения

- Один локальный пользователь без административных полномочий через API. Повторная инициализация отклоняется.
- Пароль: PBKDF2-HMAC-SHA256, 600 000 итераций, случайная соль 16 байт. В состоянии хранятся только хеши токенов.
- До 64 сессий, срок 30 дней; logout сохраняет отзыв на диск. Вход ограничен 10 попытками в минуту с одного адреса (IPv6 — с одной сети /64), 100 попытками в минуту на сервер и двумя одновременными вычислениями пароля. Заголовки `X-Forwarded-For` не учитываются: за обратным прокси все клиенты делят один адрес.
- Состояние: `data/state.json`, схема v1, права 0600, атомарная замена и fsync. Одновременный запуск на одном каталоге блокируется. Повреждённый файл не сбрасывается автоматически.
- Размер тела запроса — до 64 KiB; состояние — до 4 MiB. JSON-хранилище предназначено для M1, не для большого медиакаталога.
- Сессии, настройки и состояние просмотра переживают штатный рестарт и `SIGKILL` посреди записи (проверка `make e2e`); временные файлы прерванных записей удаляются при следующем запуске. Восстановление после отключения питания, NAS-файловые системы и миграция с Emby не проверены. Для копии состояния остановить Coach и скопировать приватный каталог `data`.
- WebSocket отправляет UserDataChanged после сохранения «просмотрено», «избранное» и прогресса — всем активным соединениям этого пользователя. На соединение допускается 32 ожидающих события; при переполнении оно закрывается, не задерживая API и других клиентов. Журнала/повторной доставки нет: после переподключения нужно перечитать состояние через API.
- Logout закрывает все WebSocket-соединения своей сессии, не затрагивая другие. Действительность токена проверяется перед событием, при входящих кадрах и каждые 20 секунд при ping; остановка Coach закрывает открытые соединения.
- Другие серверные события, удалённое управление, администрирование, перекодирование видео и собственный frontend не реализованы.

## Проверка

```sh
go test -race ./...
go vet ./...
go build -o bin/coach ./cmd/coach
node scripts/check-emby-client.mjs
COACH_CHECK_MEDIA=1 node scripts/check-emby-client.mjs
COACH_WEB_DIR=../emby-webui COACH_CHECK_MEDIA=1 node scripts/check-emby-client.mjs
```

Сценарий требует Node.js с `fetch` и глобальным `WebSocket`. Он создаёт временного пользователя и каталог, запускает/перезапускает Coach на свободном loopback-порту и проверяет обмен оригинальных API-модулей. С `COACH_WEB_DIR` модули читаются из локального UI; без него нужен доступ к Emby. Данные рабочего Emby не изменяются; тестовые процессы останавливаются, временное состояние удаляется.

Вариант `COACH_CHECK_MEDIA=1` требует FFmpeg и FFprobe: генерирует синтетическое видео, проверяет каталог/метаданные, пропуск битого файла, стабильный ID, согласование PlaybackInfo оригинальным API-клиентом, байты потока, HEAD/Range/416/401, сохранение позиции после рестарта и завершение просмотра. Исходник проверяется по SHA-256. Без переменной выполняется сценарий пустой библиотеки.

Другой экземпляр/бинарник можно указать через `EMBY_REFERENCE` и `COACH_BINARY`. Проверка ожидает web-версию 4.10.0.40; изменение версии требует пересмотра контракта. В отчёт выводятся SHA-256 модулей и маршруты без токенов. События приложения и хранилище браузера заменены минимальными адаптерами. В медиасценарии оригинальный ApiClient открывает WebSocket, принимает UserDataChanged и переподключается после рестарта; проверяется закрытие при logout. DOM, плеер и connection manager не проверяются.

Те же команды есть в `Makefile`: `make` (lint, test, build), `make lint` (golangci-lint v2 по `.golangci.yml`, включая go vet и проверку gofmt/goimports; устанавливается отдельно), `make vet`, `make build-linux` (Linux amd64, `CGO_ENABLED=0`), `make check` (сборка и Node-сценарий; переменные окружения передаются как выше), `make e2e`, `make e2e-report`, `make clean`. `make lint` проверяет и модуль `e2e/` тем же `.golangci.yml`.

CI ([ci.yml](.github/workflows/ci.yml)) запускается при push в `main` и в каждом pull request. Этапы идут последовательно, каждый следующий — только после успеха предыдущего:

1. Сборка: golangci-lint v2.14 для обоих модулей, `make build build-linux`.
2. Тесты: `make test` и `make e2e` в `golang:1.25-alpine3.24` с FFmpeg 8.1, как в образе, от пользователя без прав root. С FFmpeg 6.1 и 7.1 (Ubuntu 24.04, Debian 13) тест перемотки HLS падает (#64).
3. Контейнер: сборка образа и `scripts/check-container.sh` на linux/amd64 и linux/arm64.

Сборка и тесты идут на Go 1.25, минимальной версии из `go.mod`; образ собирается на Go из `Dockerfile`. Node-сценарий (`make check`) в CI не запускается.

### E2E по контракту

```sh
make e2e
make e2e-report
```

`make e2e` собирает Coach и генерирует FFmpeg синтетическую медиатеку: фильм с двумя аудиодорожками, встроенным и внешним субтитром и постером; сериал с `Season 00`; аудио и фото. Затем запускает экземпляры на loopback и проверяет каждую операцию `api/openapi.yaml`:

- без токена ожидается 401, если операция защищена;
- с токеном ожидается документированный успех: для операций с JSON-телом — 200, `application/json` и соответствие схеме, для остальных — любой 2xx.

GET и HEAD идут параллельно на общем экземпляре, каждая мутация получает свой. Поведенческие проверки в `e2e/behavior_test.go` проверяют сценарии, для которых формы ответа недостаточно: HLS, WebVTT, Next Up в Resume, сохранность подтверждённой позиции после `SIGKILL` посреди отчётов воспроизведения, ответ 500 без публикации изменения при недоступном для записи каталоге данных (запускать не от root). Нужны FFmpeg с libx264 и FFprobe. Прогон занимает около 20 секунд.

Длительная нагрузка запускается отдельно: `cd e2e && COACH_SOAK=10m go test -run TestSoak -timeout 30m ./...` (`COACH_SOAK_WORKERS`, по умолчанию 8). Каждый поток в цикле запрашивает каталог, карточку, PlaybackInfo, весь поток фильма, отчёт о прогрессе, каждый пятый раз заново подключается к WebSocket (поочерёдно закрывая соединение кадром close и обрывая его) и каждый десятый раз запрашивает встроенные субтитры (FFmpeg). Тест записывает RSS, число открытых файлов (`lsof`) и дочерних процессов (`pgrep`) и падает при ошибках запросов, оставшихся дочерних процессах, росте открытых файлов больше чем на 8 и изменении состава файлов каталога данных. Бюджеты ресурсов ещё не согласованы (#15), поэтому RSS только выводится. Без `COACH_SOAK` тест пропускается.

`e2e/known_failures.go` — карта ожидаемых падений `operationId` или ключ проверки → issue и причина. Она работает как `xfail(strict=True)`:

- упавший тест из карты помечается как skip с причиной;
- прошедший тест из карты роняет прогон: запись нужно удалить;
- упавший тест вне карты роняет прогон как регрессия.

TDD-цикл: удалить запись → увидеть падение → реализовать → тест зелёный. `make e2e-report` строит Allure-отчёт (Allure CLI 3) в `e2e/allure-report`. Заголовок теста — `summary` операции; метки: epic (Contract или Behavior), feature (сервис Emby), story (`operationId`); запросы и ответы приложены к шагам; у ожидаемых падений есть ссылка на issue.

В ограниченной среде Go может потребовать доступный `GOCACHE`, а сетевые тесты — разрешение на loopback-соединения. Результаты текущего запуска: [VALIDATION.md](docs/VALIDATION.md).
